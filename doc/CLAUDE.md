# BMS Project Rules

## Start of every session
- Read `doc/progress.md` (task list and status) and `doc/bms-prompt.md` (full spec).

## Project memory
- This file is the project's memory file (user decision, instead of a separate `memory.md`). Every new instruction or decision for this project is written here, never in session/auto memory.

## Decisions that override `doc/bms-prompt.md`
- Java: JDK 21 (installed). JavaFX 21.x (JavaFX 25+ needs JDK 23).
- Config: YAML, not `application.properties`.
  - `application.yml`: active profile (`app.profile`), app name, version, GitHub API.
  - `application-{dev,stage,prod}.yml`: DB, pool, admin.
  - All profiles use the same DB name; the user manages profiles.
- Status/type columns: Java enums stored as VARCHAR. No status lookup tables.
  - Every enum column is listed in `DataSeeder.ENUM_COLUMNS`: Hibernate's CHECK on it never updates, so a new enum value fails on insert until startup drops the outdated CHECK.
  - hbm2ddl never resizes a column: a size change needs a guarded step in `DataSeeder.migrateColumnSizes` (`SchemaRepository.widenDecimal`). Stock cost (`stock_ledger.unit_price`, `avg_cost_after`) is DECIMAL(16,4); money shown is rounded to 2.
  - Exception (user decision): account types are a user-managed table `account_types` (Bangla/English name + number rule), seeded with Cash, Bank, bKash, Nagad, Rocket (the last three have the mobile rule; data fix v5 adds them to an existing DB, keeping any the user already has; v6 removes the old generic "Mobile banking" type unless an account uses it).
- Accounts module: only admin and manager (user decision). Cashier, and any staff/employee login or new role added later, gets no Accounts permission. An account can be switched off only while its balance is exactly 0 (N13, `AccountService.setStatus`); an off account is hidden from every pick list (`AccountRepository.all`), but stays at the bottom of the Accounts list (status column) with its ledger, and can be switched on again; every other button on an off row is disabled (edit, ledger, double-click).
- Dashboard (`DashboardService`, user decisions): a date range on top (today at first; clearing it goes back to today; no refresh or today button, user decision) changes the whole page: sales, purchases, expenses, net cash and profit are for those dates; party, account and stock figures are as at the end of the last day. Every role that may view it sees all of it, account balances and profit included (an exception to the Accounts rule above). Net profit = sales (minus goods returned) − cost of those goods (average cost when sold; returns at the sale’s own price) − expenses − the worked-out salary of the range’s months (paid or not). The whole month’s salary is charged even for a one-day range (user decision, not pro-rated); the salary line is labelled "বেতন (পুরো মাসের)" so it is not taken for a mistake. Net cash = money into all accounts − money out, transfers left out. Dashboard tables show `dashboard_rows` rows a page (Settings, default 5).
- One-time fixes to existing data go in `DataSeeder.migrateData()`, numbered by `data_version` in app_config (never re-run, so admin edits stay).
- Pack sizes (user decision): the same goods in different pack sizes (e.g. rice in 50 / 25 / 20 kg bags) are separate products, each with its own stock, price and conversion. No product variants / multiple packs per product. Product names may repeat; only the same name + same unit, secondary unit and conversion is a duplicate. Wherever a product is picked or listed (stock, sales, purchases), show its conversion next to the name so same-name products can be told apart.
- Ledgers: party balance = opening (+ receivable / - payable) + debit - credit; debit = what we gave (goods sold, money paid), credit = what we got. Screens say দিলাম / পেলাম and "৳X পাবো" / "৳X দেবো" (`PartyText`). Money moves write through `AccountLedgerService.post` / `PartyLedgerService.post`; lock order: party row, then the sale/transaction row, then product rows (by id), then account rows (by id).
- Sales (`SaleService`): memo no. per type from `MAX(memo_no) FOR UPDATE` + unique index; items keep `main_quantity` (stock unit) so later conversion edits never change past sales; a walk-in customer (no party) cannot owe; returns credit the party, refunds optional. Wholesale / retail price is chosen per sale ("দামের ধরন", starts at retail); parties have no wholesale/retail field (user decision; `parties.party_type` is left unused). Sales return refunds (user decision, N9): coins may be short, so a refund may differ from the goods' value by under ৳1 (`SaleService.refundRounding`): a walk-in customer more or less, a party only more (less stays in its ledger as credit). The difference is a real loss / gain and is added to `returned_amount` and to the party's return credit, so cash, profit and ledger agree; it is never hidden in a note. The next return's "still worth" cap is counted from the returned goods, not from `returned_amount`. Part returns work out stock on the total returned so far (`PurchaseService.mainShare`, N7). Purchase returns are not changed. A sale with no money typed (total above 0) first asks whether to sell it all on credit (N11, user decision). A party may pay more than the bill: the sale gets only the bill, the extra is a plain party receipt (source PARTY); a walk-in cannot overpay. One payment row per account. Sale screen (user decisions): the bill discount comes off the whole bill, VAT included (grand = subtotal + VAT on the subtotal − discount; screen order total, VAT, discount; it may be as big as the bill, so a paisa can be dropped from the total); an amount filled by "পুরো টাকা" follows the bill when VAT, discount or items change, until the user types an amount himself. Money rows (sale and purchase): at least one account row always stays, so the only row has no remove button; each row's account shows its type in brackets (`AccountFormController.nameWithType`), and on a purchase the picked account's balance shows small under the row.
- Memo print (N6, user decisions): paper is picked in Settings (`memo_paper`: A4, A5 or 80 mm roll; default A5, `MemoPaper`). Texts in the app's language. Print first shows a preview (`MemoViewController`, page built by `SaleMemo`), then the printer dialog (`NodePrinter`: scaled to the paper's width; a long memo goes on more sheets, cut only between rows; the roll uses the printer's longest 75–85 mm paper at least 200 mm long; a printer with no roll, e.g. PDF, gets the narrow paper nearest 80 mm, on several sheets (user decision); else the dialog's paper with the memo 72 mm wide). JavaFX cannot print on a paper of the memo's own length: it turns any custom size into the nearest standard one (`MediaSize.findMedia`). The memo shows the shop (logo, name, address, mobile, email), memo no., date, customer, goods, totals, returned, paid, due, each account the money went into (installments with their date), a party's balance before this sale and now (বাকি / জমা, never পাবো / দেবো: the customer reads it), thanks and two signature lines. Print sits on each sales list row; after a sale is saved the app asks "Print memo?".
- Product labels (20.4, user decisions): ZXing (`com.google.zxing:core`, `CodeImage`) makes a Code 128 barcode or a QR code from the product's SKU; the user picks which. The Products row button "লেবেল" opens a window (`ProductLabelController`): kind, number of labels (1-240), a preview of the sheet, then Print on A4 through `NodePrinter` (three labels on a row, each with name, the code and the retail price; no SKU text under the code (user decision); a row is never cut). a SKU with non-ASCII characters cannot be a barcode (QR still works). A new product's code is filled in automatically (`ProductService.nextSku`: P and five digits counted from the biggest product id, skipping taken codes; also on a copy); the user may change it but cannot clear it: every product has a code (user decision; `SKU_REQUIRED`, a required field in the form). Data fix v7 gives each old product without a code one (P and five digits from its id, skipping taken codes); editing a product that has none fills the next code.
- Barcode scanner on the sale screen (20.5): a scanner is a keyboard that types the code and Enter. Enter in the product field with text that is exactly a product's SKU (`ProductService.findBySku`) adds that product at once (1 in its main unit, price of the chosen retail / wholesale type; scanning it again adds one more to the same line; the stock is checked; no price set = the product is picked the usual way). Any other text is the ordinary search. The same product in the same unit at the same price and discount is one line on the sale screen (a second add, by hand or by scanner, adds to the quantity). The sale and purchase entry pages give the lines 70 % of the width and the totals panel 30 % (`mainPercent="70"`), so the quantity buttons never push the row buttons out of sight. The quantity input of a new line is a number field (user decision): small ▲ ▼ arrows inside the box at its right edge change it by one (sale and purchase); the lines table has − and + around each quantity.
- Purchases (`PurchaseService`, user decisions): no VAT, bill discount only, shared over the lines so each line's stock cost is what was really paid; a cash purchase without a supplier must be paid in full; optional supplier memo no. (`transactions.supplier_memo_no`, searchable); each purchase row has a "pay the due" button. A purchase return leaves stock at its purchase cost and the average cost is worked out again (`StockLedgerService.post`, PURCHASE_RETURN with a price). Money out never goes above what the account holds on that date. Sales and purchases share `TransactionRepository` (one per type); purchase lines in the party and account ledgers say "ক্রয় মেমো #n" so they are not taken for a sale's memo.
- Expenses (`ExpenseService`, user decisions): categories are called "খাত" on screen (Bangla + English name only; no category type: "খরচ তো খরচ"; the old `expense_categories.type` column is kept but unused, made NULL-able with its CHECK dropped by `DataSeeder.migrateUnusedColumns`); five common ones are seeded when the table is empty. Each expense is one account DEBIT with source EXPENSE (`reference_id` = the expense). An expense may be edited or deleted (users with that permission); its ledger entry is then replaced or removed in the same transaction, the only ledger entries ever changed. A category with expenses cannot be deleted.
- Users are the staff (N12, user decisions; replaces the Employees page of Stage 14):
  - One `users` table holds the login and the staff details (mobile, NID, address, join date, salary type, salary). No employees table and no attendance (both dropped with their test data by `LegacySchema` before Hibernate builds tables).
  - Role (পদ) = admin / manager / cashier / employee (`UserRole.EMPLOYEE`); what each may do is set in Permissions (employee: nothing at first). The admin gets a salary too.
  - Salary is on the Users page, admin only (`SalaryService.requireAdmin`); the old EMPLOYEE permission section is gone.
  - Monthly salary is never cut automatically. Daily pay = days × rate, hourly = hours × rate; days / hours are typed in.
  - One popup works out the month and pays in the same save (`SalaryService.save`); the money part is optional. A cut (deduction) needs its reason (`salary_processing.note`).
  - A payment can never be more than the month's due, except an emergency advance ("জরুরি অগ্রিম", `salary_payments.emergency`). Whatever a month gets above its net carries forward as paid for the next months (`SalaryService.chain`). Due is never shown below 0: "অগ্রিম বাকি ৳X" instead. Payments go in `salary_payments` (user + salary month), each an account DEBIT with source SALARY; a payment can be deleted from the history (money back to the account), not edited.
  - A user with salary due or advance not yet earned cannot be made inactive. A registration has no salary until the admin edits it; it is not on the salary sheet until then.
- Expenses page is one page, no tabs (user decision): `TwoColumnLayout` with the expenses on the left (filters: month + year, which fill the date range with that month, and a free date range; no note search; five tiles on one line: total, count, today, daily average up to today, category spent most) as one table grouped by category (`TreeTableView` via `TableHelper.setUp/fitColumns(TreeTableView)`: a bold category row with total and share, largest first, its expenses under it newest first; a click opens/closes a group; edit on expense rows only), the categories on the right.
- Reports (Stage 16, `ReportService`): each report is a `ReportTable` (title, filters text, typed columns TEXT/MONEY/NUMBER/DATE, rows, optional totals row); the Reports page (`ReportsController`: list on the left, only the filters a report uses) shows it and `ExcelExporter` (Apache POI) writes the same table to .xlsx (real numbers and dates). A new report = one method in `ReportService` + one entry in `ReportsController.Report` + its text keys. Sales/purchase/expense summaries group by day / month / year of a date range; profit and loss uses the dashboard's rules (whole-month salary) and is monthly or yearly only; party ledger: one party (that ledger is the file's one sheet) or all (user decision: the first Excel sheet is the all-party summary, then one ledger sheet per party, named by the party, via `ReportTable.more`; the page shows only the summary), open date range = all time; due collection and payable list parties with a balance above / below 0. VAT report (20.1): month filter, one row per day with sales; VAT charged is the sale's `tax_amount`; the VAT of returns is not stored, so it is the bill's VAT shared by returned ÷ grand total; VAT to pay = charged − returns. Mobile payment summary (20.3): date range; one row per account of the mobile rule (bKash, Nagad, Rocket ...) with money in, money out and net, transfers left out like the daily cash report; accounts with nothing still show 0.
- Users page (Stage 17, admin only, `UserService` / `PermissionService` / `AuditLogService`; each checks the session is an admin): three tabs (users, permissions, audit log; user decision: no separate salary tab, salary is on the users tab). Users: month and year pickers (this month at first) with the month's four totals (total, advance carried, paid, due) above one users table (no separate inactive table; with the month's net, paid and due columns (a dash when a user has no salary), active first, inactive last, a status column, and on an inactive row only the switch-on button works, the rest is greyed out) with the registrations waiting for approval (N1) beside it, shown only while there are any (a third of the width); each row: edit, salary (work out and pay), history (the salary button carries the word "বেতন", the history button "দেখুন", like edit), inactive / active (nobody can switch their own login off: that button is greyed out on their own row); username cannot change after saving; mobile, role, salary type and salary are required; a new user starts as employee; a user cannot change their own role or switch themselves off; the last active admin can never be switched off, demoted or deleted; delete only for a user with no audit-log rows or salary rows (else make inactive); passwords are BCrypt, at least 6 characters, never in the audit log; an inactive user cannot log in, a session already open runs until logout. Permissions: only manager, cashier and employee are edited (the admin always has everything), the user-management module is never editable; add / edit / delete imply view; dashboard and reports are view only; permissions are read at login, so a change reaches a user at the next login; the editor registers with `UnsavedWork`. Audit log: filters dates (this month at first), user, section; newest first; old / new values cut in the table and full in the row tooltip; a record kind with no text key shows as stored.
- Passwords (N10, user decisions; N3 dropped; a recovery-code idea was rejected): the admin password in the profile ymls is `123456` (public, so only a first password: `DataSeeder.seedAdmin` sets `must_change_password`; it matters only for a new DB, an existing admin keeps their password); the DB password stays in the yml (the DB is `localhost`). `AuthService.login` returns `MUST_CHANGE_PASSWORD` without starting a session; `setFirstPassword` then `startSession`. A user the admin creates, or sets a password for (another user), must pick their own at the next login; the admin's own password change in the form does not. A forgotten password has no self-service reset: the login screen says to ask the admin, or the support team if the admin forgot it.
- Registration (N1, user decisions): the login page has two buttons, Login and রেজিস্ট্রেশন; রেজিস্ট্রেশন opens a page (not a popup) in place of the login page, with a back-to-login button (`WindowManager.showRegister`, `RegisterController`). Anyone may register (`RegistrationService`); the user is `UserStatus.PENDING` (role column holds CASHIER until then) and cannot log in ("not approved yet"). On the Users page the admin approves it, picking the role (no default), or rejects it, which deletes it; after approving, the admin edits it to set the salary (N12, registration itself unchanged). The password is the user's own, so no change at the first login. The registration's audit row has no user, so a rejected one can be deleted.
- Support login (`SupportAccount`, role `SUPER_ADMIN`, username `emranhos1`): the support team's own hidden login. Its password is never written anywhere in the repo (public): only a BCrypt hash in `SupportAccount.PASSWORD_HASH`, made with `com.eh.bms.tools.SupportHashTool` from a long random password (16+ characters) kept by the support team; blank hash = no support login. `DataSeeder.seedSupport` creates it and keeps its hash in step with the code (a release can change the password). It acts as an admin (`UserSession.isAdmin`), never shows in the users list or the audit log's user filter, and `UserService` never finds it, so the app cannot edit, switch off or delete it; its changes show in the audit log as "BMS Support". It resets any admin's or user's password from the Users page.
- Release (Stages 18–19, user decision: copied from the finance-app project's code, overrides bms-prompt.md's tag trigger, `version.json`, generated notes, `updater.bat`):
  - Claude bumps `<version>` in `pom.xml` and writes `release-notes/v<version>.md` (English, `<!-- bn -->`, Bangla). The user pushes `dev-emon` → `development` → `stage` → `production`.
  - `.github/workflows/release.yml` runs on push to `production` and releases only when the pom version has no `v<version>` tag yet and the notes file exists. `app.profile` is the user's choice and is never checked or changed (a dev-profile build is fine).
  - Build: `bms.jar` + `lib/` (dependency jars copied by `mvn package`, on the jar's Class-Path) → jpackage app image → Inno Setup (`packaging/bms.iss`, never change its AppId) → `BMS-Update-<version>.exe` + `.sha256` on the GitHub Release.
  - Login screen (`UpdateService`, `app.github.repo`): background check, banner above the card on every PC with an older version, the user picks the download folder (last one remembered, else Downloads; only installers the app downloaded are ever deleted), size + SHA-256 checked, then the installer's wizard opens and the app closes.
- Backup (Stage 20, user decision): exactly the finance-app way, nothing else. `mysqldump` / `mysql` local backup and restore, Google Drive backup and restore in a `BMS` folder, and at logout the question Backup now / Skip & logout / Cancel. No backup on app close: the old `auto_backup` setting goes (data fix v8 deletes the row).
  - Code: `BackupService` (local, finds the MySQL tools on the PC), `GoogleDriveService` (one shared instance; sign-in token kept in `tokens/` under `AppPaths.dataDir()`, because the install folder is not writable; `connectIfStored` opens the connection from the token with no browser), `DriveBackupService` (dump → Drive, Drive → restore; the dump goes to the temp folder and is deleted after). Settings is two rows of two cards (user decision), the cards of a row as tall as each other: business | app settings, then (admin only, `backupRow`) "এই কম্পিউটারে" (`LocalBackupController`, `backup-local.fxml`) | Google Drive (`DriveBackupController`, `backup-drive.fxml`); `BackupJobs` runs one job at a time for both, all in one popup (user decision): the question, then (after Yes) the same popup becomes a loading screen, then it shows the result (red for an error) with a Close button; no top-bar message for backup jobs. And the logout question (`LogoutBackupDialog`) are for role ADMIN only (the support login is left out). `credentials.json` and `tokens/` are in `.gitignore`.
- Times are picked on a clock (`TimePicker`: hour, then minute, AM/PM), never typed (user decision). No screen uses it since attendance went (N12); it is kept for the next time field.
- Date range filters use `DateRangePicker` (one field, first and last day on one calendar), never two DatePickers. Every filter bar has a clear button.
- No IService interfaces (user decision, overrides bms-prompt.md rules 5/6): controllers use the concrete services.
- Names the user enters for master data (accounts, account types, ...) have a Bangla and an English name, shown by language (`I18n.pick`).

## Dev login skip
- `dev.auto-login: <username>` in `application-dev.yml` opens the app logged in as that user (`AuthService.devAutoLogin`). Works only when `app.profile` is `dev`; blank = login screen. User decision: keep it blank (login in dev too, so the first-login password change and the other login screens are really used); set it only when asked.

## Build
- Before every build, show a big warning with the current `app.profile` value. Never change the profile.
- System `JAVA_HOME` is JDK 11 (user keeps it; never change it or suggest it). JDK 21 is at `C:\Users\USER\.jdks\ms-21.0.12.1`.
  - Own tool calls: prefix every `mvn` with `$env:JAVA_HOME = "$env:USERPROFILE\.jdks\ms-21.0.12.1";`.
  - The user runs `mvn21 javafx:run` (alias in `~/.bashrc`); tell them `mvn21`, not plain `mvn`. `.vscode/settings.json` (gitignored) sets JDK 21 for the editor.
  - "Unresolved compilation problem" on run = stale classes in `target/` → `mvn clean`.
- Screenshots or run logs taken to check the app: delete them right after checking (`Remove-Item -LiteralPath` with the absolute path); they capture the user's whole screen.

## Forms and messages (every page)
- Number fields: `InputFilters.digits` / `InputFilters.decimal` (no letters, Bangla digits → 0-9). Text: `InputFilters.maxLength`.
- Validation: `FormValidator`. Check all fields, show every error (red box + message under the field), focus the first.
- A hint/error label whose text is set directly takes no space while empty (`FormValidator.hideWhenEmpty`); no blank gaps under fields.
- Every save/delete: `Dialogs.confirmSave()` / `Dialogs.confirm(...)` first. Deletes use `Dialogs.confirmDelete(...)` (red Yes button).
- Result and general errors: `Notifier.success` / `Notifier.error` (top bar, 5 s). No status labels on the page.
- Layout: label column 200 px, labels top-aligned (`form-label`, all bold; add `required` for a must-fill field, which shows a red asterisk — never mark it in the text); every input fills the second column, same width everywhere. Exception: form cards side by side on one page (Settings) size the label column to their longest label.
- Buttons: one class per action — `save-button`, `add-button`, `edit-button`, `delete-button`, `cancel-button` (red), `view-button` (opens a read-only window, e.g. a ledger) (also `login-button`, `page-button`, `no-button` = grey No in confirm dialogs, `icon-button` = action on a table row via `TableHelper.actionsColumn`, exempt from 140 x 36). All are 36 px high and at least 140 px wide; a longer label makes the button wider, never cut (Login: full card width). Keep labels short. Their look lives only in the "Buttons" block of `main.css`; change it there to change every such button. Never leave a button unstyled.
- Popup forms: 540 px wide, one field per row (`form-row` + `form-row-label`), Bangla and English names on separate rows. Optional rows hide with no gap.
- Every popup (forms, ledgers, Yes/No) opens through `WindowManager.dialog`: no window title bar (user decision); the full title stands turned 90° on a dark strip on the left (drag it to move). Every popup needs its own close/cancel button; Esc also closes. Yes/No questions go through `Dialogs`, never `Alert`.
- Pages with a main part and a side part (e.g. Accounts + Account types, Settings: business + app cards): root `TwoColumnLayout` (62/38, or `mainPercent="50"` for two equal parts; stacks the side part under the main part on a narrow window or when a part would get less than its own minimum width, the page scrolls). A page title bar (title left, search + buttons right, user decision) is an `HBox` with a growing spacer and a search that can shrink (`minWidth`); a filter bar (several filters) is a `FlowPane` so it wraps.
- Per-row actions (ledger, money in/out, inactive, ...): icon buttons in one column via `TableHelper.actionsColumn` (`icon-button` + colour class, SVG icons from `Icons`, tooltip says what it does), edit first. The toolbar keeps only "New ..." and page-wide actions (e.g. Transfer). Delete sits in the edit form, shown only when the record can be deleted (e.g. a party with no history and earlier balance 0). A button can be shown or greyed out per row (`RowAction` visibleWhen / enabledWhen).
- Parties are never deleted once used; they are made inactive (`parties.status`) and listed in the same table, last, with a status column; on an inactive row only the switch-on button works, the rest is greyed out (`RowAction.enabledWhen`), the same for accounts and users. Pickers (sale, purchase, ...) show active parties only. A party with money due cannot be made inactive. Forgive (user decision, `PartyService.writeOff`): a "মাফ" button on an active party row with any balance (they owe us, or we owe them; e.g. a customer who died or went away) adds one `WRITE_OFF` ledger entry that brings the balance to exactly 0, after a confirm, with an audit row; the sales and purchases stay as they were, but the forgiven amount (what was owed to us minus what we owed) is taken off the profit: the dashboard profit card has a "মাফ করা বাকি" line, the profit and loss report a column, and a report "মাফ করা বাকির তালিকা" (date range) lists each one (user decision).
- Table column widths fit their text (`TableHelper.fitColumns`, run by `PaginatedTable`); never set column widths by hand.
- Double-click on a row opens its view (ledger / details, same as the "দেখুন" button), never the edit form; a table with no view button has no double-click.
- Every table row shows its full data in a tooltip while hovered (`PaginatedTable` → `TableHelper.installRows`; default "heading: value" per column, or `TableHelper.rowTooltip` for more, e.g. products). So lists show only the main columns. A long value in a tooltip wraps as a `Text` with a fixed wrapping width, never a wrapping `Label` (that made the tooltip as tall as the screen). Row colours via `TableHelper.rowStyle`, never a custom row factory.
- List popups (ledgers, sale details) get their size from `WindowManager.sizeListWindow` (capped to the screen; the content fills that height so the buttons under the table stay in sight, and scrolls only if it cannot shrink enough); popups cannot be resized.
- Money or stock going out on a past date is checked against the lowest balance from that date on (`AccountLedgerService.availableOn`, `StockLedgerService.availableOn`), never today’s balance only.
- Popups taller than the screen scroll (`WindowManager.dialog`); forms are never squeezed. A form's `dialog-buttons` row is moved under the scroll, so it is always in sight; a round down-arrow shows in its own strip under the scrolling part (never over the content) while more is hidden below.
- A page whose root is tabs uses `PageTabs`, not `TabPane` (a TabPane hides its tab's min height, so the page is cut off instead of scrolling).
- Mobile number: exactly 11 digits, any start (no prefix rule), required where asked.
- Dates and times: `DateUtil` only (`date_format`, `time_format` 12/24-hour; Bangla digits in Bangla mode via `I18n.digits`). Files the user adds: under `AppPaths.storageDir()`, path stored relative (`AppPaths.toStored`).
- Every new text key goes into both `messages_bn` and `messages_en`.
- Texts are one short, meaningful sentence; no long explanations (user decision). English texts use a curly ’, never a straight apostrophe (MessageFormat drops it).
- A page with input a reload would lose registers with `UnsavedWork`; the language switch then asks Save / Don’t save / Cancel (`Dialogs.askSave`).

## Task workflow
- Work in small tasks from `doc/progress.md`.
- After a task: test it, mark `[T]`. Mark `✅` only after the user approves.
- Do a stage's tasks back to back, without waiting for the user to test each one. At the stage end guide the user step by step through the whole stage's test; the user tests it all at once, by hand. Do not run tests through an agent or any automated app driving for now (user decision). Still stop and ask when a real decision is needed (design, index approval, ...). When all tasks in a stage are `✅`, add ✅ after the stage title.
- New ideas go to the "New Ideas" section, numbered, split into small tasks.
